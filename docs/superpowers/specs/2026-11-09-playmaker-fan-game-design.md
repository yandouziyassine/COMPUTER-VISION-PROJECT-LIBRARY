# Playmaker: a daily football decision game built on the AI coach

Date: 2026-11-09 · Project 20 → product · Owner choices (chat, 2026-11-09): fan game only (no team tool yet); daily
challenge + free play; anonymous play with crowd stats; scoring by rank among the options with close calls; own
brand; **everything on AWS (promo credits), CloudFront address until a domain is bought**; name **Playmaker**.
Builds on `2026-11-01-football-ai-coach-design.md`, `2026-11-02-player-profiles-design.md`,
`2026-11-02-coach-insight-design.md` and the cut-back fix (arrival value).

## 1. Goal and success criteria

A free, phone-first web game. Each day every player gets the same 5 frozen moments from real professional matches,
picks what the ball carrier should do (pass to a teammate, carry, shoot), then sees the AI coach's pick and reasons,
the pro's real choice, what happened in the next 15 s, and how the crowd chose. A free-play mode replays full matches
with the coach (the current portfolio demo).

First month after public launch: ≥ 100 real players; ≥ 40 % of players who start a day finish all 5 moments;
AWS cost < $2 / month; no outage longer than one hour. Everything shown is the model's opinion, measured honestly
(the coach's limits from the project README are repeated in an "About the AI" page).

## 2. Health check of the existing system (2026-11-09) and what this design fixes

| # | Problem | Fix in this design |

| 5 | Weak value model (~2 % of variance), 27 matches, xT slightly ahead | Product framing: "model opinion" + close-call scoring (section 4); limits page |
| 6 | Python and TypeScript engines; parity fixture regenerated by hand | Fixture rebuilt with each content release and stamped with a hash of `models.json`; CI fails on mismatch |
| 7 | 7.9 MB of match data in the portfolio repo | Game content lives in S3; the portfolio demo stays as is and links to Playmaker |

## 3. Architecture

```
 OFFLINE (laptop, Python library)                 AWS (us-east-1, CDK, pay-per-use)
 coach.game_content ──► content-v{n} ──CI──► S3 content bucket (private, read via CloudFront OAC)
   held-out models,       (GitHub Release       public/ : days/<date>.json, moments/<id>.json, matches/<id>/…
   20 refits, filters,     asset = backup)      answers/: answers/<id>.json   (never served by CloudFront)
   answers split off                          S3 app bucket: the built web game
                                               CloudFront (one address, HTTPS, caching, security headers)
 Browser (TypeScript game) ◄──────────────────►   /            → app bucket
   2D / 3D view, free play engine                 /content/*   → content bucket public/ (+ CloudFront Function:
   streak + history in localStorage                               no day later than UTC today + 1, so every time zone has its own "today")
                                                  /api/*       → API Gateway HTTP API (throttled)
                                                                   → Lambda (Node 22, TypeScript)
                                                                       reads answers/ (cached in memory)
                                                                       DynamoDB (on-demand, TTL)
```

- No Python on AWS: models run offline; the API only reads precomputed scores. One source of truth per content
  version.
- Content is versioned (`v{n}`). A model change ships as a new version; days already published never change.
- Infrastructure as code (AWS CDK, TypeScript). Nothing is created by hand in the console.
- Region us-east-1 (CloudFront certificates and budgets live there; one region keeps it simple).

## 4. Content: moments and scoring

**Candidates.** Every synced pass decision of the 27 open matches (7 IDSSE Bundesliga, 20 SkillCorner A-League),
about 18,000. Each match is scored with models trained without it (the `report.held_out_models` rule): the coach
never "remembers" the answer. Options are the coach's options at the release frame (passes to each teammate, carry,
shot), with the arrival value for pass targets.

**Quality filters.** 22 tracked players visible; ball within 2 m of the carrier; no position jump > 1.5 m between
consecutive frames in the 3 s lead-up; open play only (no set pieces); ≥ 3 options; the pro's chosen option is one of
the options (the intended receiver is known).

**Uncertainty (20 refits).** For each held-out match, the pass, value, arrival and shot models are refitted 20 times
on bootstrap resamples of the training matches (whole matches, seed fixed). For each option o:
`share_top(o)` = fraction of the 20 refits in which o has the highest coach score (ties count for every tied option).

**Points (0–100 per moment).**
- 100 if o is the main model's top option or `share_top(o) ≥ 0.2` ("among the best"; several options can share it).
- Otherwise the remaining options are ordered by the main model's score; with R of them, the best gets 90, the worst
  0, linear in between: `points = round(90 · (R − rank) / (R − 1))`, rank 1..R; if R = 1 the option gets 45.
- "Pro instinct" badge (no points) when o is the pro's real choice.

**Interest score and daily sets.** interest = spread of option scores (IQR) × stakes (V(now) percentile) with bonuses
for cut-backs, AI ≠ pro, and a shot or goal within 15 s; moments where every option is "among the best" or one
option takes all 20 refits with a gap above the 95th percentile ("obvious") are dropped. The top ~1,500 form the pool.
A daily set has 5 moments: one build-up (own third), two midfield, two final third, difficulty (1 − mean points of the
options) rising from moment 1 to 5, at least one followed by a real shot or goal, no two from the same match, no
match used on two consecutive days. Days are generated 60 days ahead; a private review page lists the next 14 for a
veto (a vetoed moment is replaced by the next-best one with the same zone).

**Files (JSON, validated by `schemas/`).**
- `public/days/<YYYY-MM-DD>.json`: `{schema, content_version, day_number, date, moments: [moment id × 5]}`.
- `public/moments/<id>.json`: league, teams, minute, score, attacking direction, the release frame (positions and
  velocities, ball), 3 s of lead-up (int16 cm, 12.5 fps), options `[{k, kind, target}]`, credit line. **No scores, no
  pro pick, no outcome.**
- `answers/<id>.json`: per option `{k, score, p, value, share_top, points, reasons[≤3]}`, `ai_pick`, `pro_pick`,
  `outcome {kind: kept|lost|shot|goal, net_xg_15s}`, `models {content_version, trained_without, refits: 20}`.
- `public/matches/<id>/…`: free-play matches (the current h0/h1/z0/z1 + match/models/report format), first release:
  the 7 IDSSE matches; A-League in a later release.
- Credit lines on every screen that shows data: "Bundesliga tracking and event data: Bassek et al. (2025), DFL /
  Sportec Solutions, CC BY 4.0" and "Tracking and event data: SkillCorner open data (MIT)". No broadcast images.

## 5. API, data model, privacy, abuse

**`POST /api/pick`** body `{player: uuid v4, moment: id, option: k}` (≤ 1 kB).
Checks: valid uuid; the moment belongs to a day ≤ the server's UTC date + 1; the option exists.
Response 200: `{points, among_best, pro_instinct, ai_pick, pro_pick, outcome, reasons, crowd}` where `crowd` is
`{k: share}` or `null` when the moment has < 20 picks. A repeated pick for the same (player, moment) returns the first
stored result (no answer changes). Errors: 400 (invalid), 404 (unknown or future moment), 429 (rate limit), 500.

**DynamoDB (one table, on-demand, TTL attribute `expires`).**

| PK | SK | Attributes |
|---|---|---|
| `MOMENT#<id>` | `OPTION#<k>` | `n` (atomic ADD) |
| `PLAYER#<uuid>` | `PICK#<moment>` | option, points, time; conditional put (first pick wins); expires after 400 days |
| `RATE#<iphash>#<UTC date>` | `RATE` | count; expires after 1 day |

`iphash` = SHA-256(source IP + daily secret salt held in SSM Parameter Store, : salt of the day = HMAC(secret, UTC date)).
IPs are never stored.

**Privacy.** No account, email, name or cookie; a random player id in localStorage; streak and history in the
browser. A privacy page states exactly this. The owner's email for alarms is passed at deploy time (CI secret) and
never committed.

**Abuse and cost.** API Gateway stage throttle 20 req/s, burst 40; Lambda reserved concurrency 5 when the account's
concurrency limit allows it (new accounts may be capped at 10; then rely on throttling); ≤ 50 picks per network per
day; crowd shares only from 20 picks; no WAF (≥ $5 / month). CloudFront response headers policy: CSP (self + the
three.js chunk), HSTS, X-Content-Type-Options, Referrer-Policy. Same origin for app, content and API (no CORS).

**Cost estimate.** 1,000 players/day × 5 picks ≈ 150k API calls / month: inside the Lambda always-free allowance;
DynamoDB and S3 cents; CloudFront inside its free allowance. Expected $0–1 / month. AWS Budgets alerts at $1, $5 and
$20 (actual) and a forecast alert at $5. Before any resource is created the owner's remaining credits and their expiry
are checked and the owner gives an explicit go.

## 6. Repository, tests, CI/CD, monitoring

**Product repo `yandouziyassine/playmaker` (public).** `app/` (Vite + TypeScript; coach engine and 3D view copied from
the portfolio site's `src/lib/coach` and `src/lib/football3d`), `api/` (Lambda handler), `infra/` (CDK), `schemas/`
(JSON Schemas shared by Python and TypeScript). Content is built in the library (`20-football-analytics/coach/
game_content.py`) and published as a GitHub Release asset of the product repo.

**Tests.**
- Content build (pytest): held-out assertion per moment; public files contain no answer fields (key scan); points rule
  and close calls on synthetic options; filters; daily-set constraints; deterministic output for a fixed seed.
- Contracts: every content file validated against `schemas/` in Python (jsonschema) and TypeScript (ajv).
- Parity: TypeScript engine vs Python fixtures to 1e-6; the fixture records the SHA-256 of `models.json`; CI fails
  when they differ.
- API (vitest, mocked DynamoDB/S3): scoring lookup, first-pick-wins, validation, rate limit, crowd threshold, error
  codes.
- App: vitest units; Playwright at 390×844 playing a full day and free play against a mocked API; Lighthouse.
- Infra: CDK assertions (buckets private with OAC, answers prefix not routed, throttling, TTL, budgets and alarms
  present, no public write).
- Post-deploy smoke on the live address: today's day loads, a pick returns a result, a repeated pick returns the same.

**CI/CD (GitHub Actions).** Pull request: lint, tests, build, `cdk synth` + assertions. Merge to `main`: deploy with
GitHub OIDC (an IAM role limited to this stack; no stored AWS keys), sync the pinned content release to S3, smoke test.
One-time bootstrap (CDK bootstrap + OIDC role) is run by the owner, signed in themselves. One production stage; local
development uses a mocked API.

**Monitoring.** CloudWatch alarms: API 5xx > 1 % over 5 min, Lambda errors ≥ 5 in 5 min, throttles > 0 for 15 min,
emailed through SNS. Log retention 14 days. Usage numbers come from DynamoDB counts (no page analytics).

**Library fixes (M0).** `20-football-analytics/requirements.lock` (pinned, generated) + `make venv`; `make results`
regenerating every results JSON with a `generated_by` commit stamp; matplotlib in `tests/requirements-ci.txt`;
raw-source URLs and SHA-256 checksums in `DATA_LICENSES.md`.

## 10. Risks

- Credits expire or run out → budgets + forecast alert; the stack can be destroyed with one command.
- New AWS accounts may have low Lambda concurrency → no reserved concurrency; throttling still caps cost.
- Crowd counts can be inflated by fake player ids → per-network daily cap, crowd shown only as shares, labelled
  "players' picks".
- Sync or tracking glitches in a moment → quality filters + the 14-day review page.
- The model can be wrong → close-call scoring, "model opinion" labels, limits page, outcome always shown.
- Name already used elsewhere → check before M4; rename is cheap before launch.
